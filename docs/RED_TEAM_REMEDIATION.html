What a reviewer has to decide before merging

Four commits change consensus.

FND-001, FND-002, FND-004 and FND-007 alter what blocks are valid. Nodes on this code reject blocks older nodes accept, so they need a coordinated deployment. Open swaps created before the fork expire back to their creators, as with PR #135.

Only Signet and Regtest can be swapped against.

A claim now proves its L1 payment against the mainchain headers the node validates, so swaps against chains without a header relay (BCH, LTC) are rejected at creation. This follows the repo's own spec, but it removes the BCH testnet flow from the GUI and CLI. The --l1-bch-testnet4 flag became --l1-regtest.

The RPC now requires a cookie.

Any script that calls the node needs --rpc-cookie-file (the CLI finds the default data directory's cookie by itself), or the node needs --rpc-no-auth. Non-loopback binds need --rpc-allow-remote.

The integration suite was not run here.

It needs bitcoind and the enforcer. The rewritten open-swap test compiles and now makes a real regtest payment with a real proof; it should run in CI before this merges.

CriticalFND-001commit fc4437027 files · +2314 −1087consensus change

Consensus never verified the L1 payment; any block producer could take an escrow

What was wrong

The only check that a swap's parent-chain payment happened lived in the mempool validator, and it read a SwapState that each node computed from its own parent-chain RPC. Block validation checked nothing about L1, and connect overwrote the local state to match the block ("trust the block").

A miner could build a claim on an open swap paying themselves, or force-complete a pre-specified swap, with no L1 payment anywhere. Every node accepted the block. PR #135 had fixed who a claim must pay, not whether anything was paid for.

What changed

Option B of the repo's own spec, docs/specs/L1_PAYMENT_PROOFS.html. A SwapClaim now carries an L1PaymentProof in the proof_data field that had been reserved for it: the merkle block from gettxoutproof (header plus branch) and the raw payment. Consensus verifies it from block data alone, on both the mempool and block paths, so the two cannot drift.

The interim mitigation the report suggested (reject blocks when the local swap is not ReadyToClaim) was not taken: it would make consensus depend on node-local RPC state and split the chain.

The verification chain, in order

Header is a known mainchain blockIts hash must appear in main_header_infos, the table the enforcer-fed archive writes. State reads it through a second handle to the same LMDB database.
…on the anchor's ancestryWalk back from the L2 header's prev_main_hash to the proof block's height; hashes must match. At most max_l1_tx_age_blocks deep.
Confirmations from the anchorDepth below prev_main_hash, so every node computes the same number. The tip's anchor is stored per height in main_anchors for the mempool.
Transaction is in the blockMerkleBlock::extract_matches recomputes the header's root and rejects the CVE-2012-2459 duplicate-hash shape.
Pays the swap's recipientAt least l1_amount to the script of l1_recipient_address, parsed for the swap's chain.
Commits to swap and claimerAn OP_RETURN of "CSFT" ‖ swap_id ‖ l2_claimer. The committed address is who gets paid; for a pre-specified swap it must equal the fixed recipient.
Claim pays that addressThe full l2_amount must reach the committed claimer. A legacy l2_claimer_address on the claim must agree.

Consequences

  • SwapCreate is rejected for chains whose headers the node does not hold and for L1 recipients that do not parse for the chain, so nobody escrows into a swap that could only expire.
  • The commitment makes the payer the claimant: nobody can present a proof of a payment naming their address without having made it. SwapAccept is coordination now, not security.
  • One payment names one swap, so L1 txid uniqueness holds by construction.
  • connect records the proven txid and claimer on the swap instead of trusting the block; swap reconstruction reads them from the proof.
  • update_swap_l1_txid and RPC-based detection are advisory: display, and the txid the node builds a proof from.

Surface

  • claim_swap(swap_id, l2_claimer_address, l1_proof): the proof is optional hex; otherwise the node builds it from its parent-chain RPC.
  • New l1_payment_commitment RPC and CLI command returns the OP_RETURN payload a filler puts in a data output.
  • App::build_swap_claim is the one claim builder behind the RPC and the GUI; the GUI pane gained a proof field.
  • Selectable chains are Signet and Regtest; default L1 configs point at local nodes on 38332 and 18443.
Tests added and files touched
Proof verification (lib/state/l1_proof.rs, synthetic regtest blocks): valid proof with confirmations counted from the anchor; unknown block; sibling block off the anchor's chain; tampered transaction; underpayment, missing and wrong commitment; pre-specified claimer mismatch; unprovable chain and bad encoding; commitment round trip.
Consensus rules (lib/state/swap.rs): claim without proof rejected; proof paying committed claimer accepted; paying anyone else, or underpaying, rejected; confirmations counted from the anchor; proof for another swap rejected; pre-specified swap requires payment to its recipient; mempool path uses the tip anchor and needs no local state; a reservation does not override the prover.
SwapCreate: unprovable chain and unparseable recipient rejected. State: sees headers the Archive writes.
Integration (integration_tests/swap_creation.rs): real regtest payment with the commitment, real proof from gettxoutproof, claim without proof refused, claim to a non-committed address refused, claim with proof completes the swap and records txid and claimer.

HighFND-002commit 0e371464 files · +293 −10partly fixed by #135

Open-swap claims were a race: nothing bound the escrow to whoever paid

What was wrong

Once a fill was detected, the mempool accepted any claimer address the claim declared. The L1 sender was recorded but never compared to anything; the L2 binding was only set through a manual RPC on one node. Anyone watching could claim the escrow first.

PR #135 introduced SwapAccept reservations, which closed the race on the block path. FND-001 then moved entitlement into the payment itself.

What this commit closes

Automatic detection matched any payment to the right address for the right amount and never set l2_claimer_address. It now reads the OP_RETURN commitment from the payment's script, records only payments that commit to this swap (and to the fixed recipient, for a pre-specified swap), stores the committed claimer, and ignores uncommitted payments with a warning: they are not fills, and a claim built from one would be rejected everywhere.

update_swap_l1_txid took a txid, a confirmation count and a claimer on the caller's word. With a parent-chain RPC configured it now looks the transaction up and takes the confirmations and committed claimer from the chain, refusing a txid that commits to another swap. Without an RPC it records the values unverified and says so, which is harmless now that claims are proven separately.

Tests added and files touched
Detection driven through an in-process JSON-RPC server: a committed payment is recorded with its claimer and marks the swap ReadyToClaim; an uncommitted payment and one for another swap leave it Pending.
  • lib/state/two_way_peg_data.rs
  • lib/parent_chain_rpc.rs (TransactionInfo::swap_commitment, hex field)
  • app/rpc_server.rs
  • rpc-api/lib.rs
MediumFND-003commit bb916002 files · +183 −5

Two-way-peg disconnect deleted from the wrong table, and its height check was off by one

What was wrong

The withdrawal-bundle branch of disconnect looked up the newest row of withdrawal_bundle_event_blocks and then deleted that index from deposit_blocks, a copy-paste of the deposit branch. After one reorg over a bundle event the withdrawal row stayed and a deposit row belonging to another block vanished, so the next reorg rebuilt the wrong 2WPD range.

Writing the regression test exposed a second bug: connect records the sidechain height at which an event block was applied, but disconnect asserted that height minus one, and the net_task search for the last row applied by an earlier block filtered on height − 1 too. Connecting a 2WPD with a deposit and then disconnecting it panicked, which would have killed the net task on any reorg across a deposit or bundle event.

What changed

  • Delete from the table the row came from.
  • Compare heights as recorded in both disconnect and net_task::disconnect_tip_.
  • A connect-then-disconnect round trip over a deposit plus a Submitted bundle event pins both tables and shows rows from earlier blocks survive.
MediumFND-004commit 16260cc4 files · +126 −17partly fixed by #135

A deleted swap record left its escrow locked, and the orphan cleanup never fired

What was wrong

The report's main vector, the delete_swap RPC removing a Pending swap while its outputs stayed locked and consensus then accepting any claim on the unknown swap, was closed by PR #135: the RPC is gone and claims on unknown swaps fail closed.

Two residuals stayed. delete_swap_unchecked only unlocked outputs in the "record missing" branch, so a future caller deleting a readable record would orphan its locks. And Node::submit_transaction triggered orphan cleanup by matching the strings "orphaned lock" and "corrupted swap" in the error text, while the regular-spend validator emitted "Cannot spend locked output", so an orphan hit through a normal transfer was never repaired.

What changed

  • delete_swap_unchecked releases the swap's locks unconditionally before deleting; rollback, its one caller, has already unlocked and finds nothing to do.
  • A typed state::Error::OrphanedLock is raised by both validate_swap_create and validate_no_locked_outputs when a lock's swap does not exist or cannot be read; the node matches on the variant.
  • Tests: unlocking on delete; typed error for an orphan versus plain rejection for a live lock; cleanup removes exactly the orphan.
MediumFND-005commit 48158d415 files · +573 −20breaking for scripts

The JSON-RPC server accepted any request from anyone who could open the socket

What was wrong

Every method that matters lives on the RPC: transfer, withdraw, create_deposit and mine (which spend the enforcer's L1 wallet), set_seed_from_mnemonic, stop. On the default loopback bind that meant any local process; with --rpc-addr 0.0.0.0, which the README showed for multi-instance setups, anyone on the network.

What changed

  • Bitcoin Core style cookie: on start the node draws a 32-byte secret and writes __cookie__:<secret> to <datadir>/rpc.cookie, mode 0600, rotated every start.
  • A tower-http validate-request layer in front of jsonrpsee answers 401 to any request without it (basic auth or bearer), compared in constant time.
  • --rpc-cookie-file moves the file; --rpc-no-auth disables the check with a warning; a non-loopback --rpc-addr is refused without --rpc-allow-remote.
  • The CLI reads the default data directory's cookie automatically; the GUI console passes its own node's cookie; the integration harness reads it from the spawned node's data directory. Shared parsing and header helpers live in rpc-api/auth.rs.
Tests added and files touched
Header acceptance and rejection (basic, bearer, wrong user, wrong secret, garbage); cookie file mode and rotation across restarts; the bind guard; a live jsonrpsee server that returns 401 without the cookie and answers with it.

  • app/rpc_server.rs, cli.rs, main.rs, gui/mod.rs, gui/console_logs.rs

  • README.md ("RPC authentication" section)
MediumFND-008commit f955cc15 files · +340 −64

Assertions in the peg state machine wedged the node on unexpected event order

What was wrong

The two-way-peg connect and disconnect path asserted its way through the withdrawal-bundle lifecycle: heights, latest statuses, RollBack::push results, the latest-failed-bundle record. These run inside task::block_in_place in the net task, so a violation killed the task and the node stayed stuck at the same block on every restart, since the enforcer replays the same events.

One assertion was simply wrong: a pending bundle collected at height N had to be reported Submitted at exactly N+1, but a slow enforcer, a delayed L1 block or a restart shifts it. The m6id already identifies the bundle.

What changed

  • The height-adjacency assertion became a debug log.
  • Every other assertion is a structured error: UnexpectedWithdrawalBundleStatus, WithdrawalBundleEventOutOfOrder, EventBlockMismatch, InconsistentLatestFailedWithdrawalBundle, LatestFailedWithdrawalBundleMismatch; the height expect in disconnect is NoTip; the reorg loop returns ReorgMissedCommonAncestor.
  • Tests: a Submitted event three blocks after collection is applied; a Confirmed event on a bundle that is not Submitted is an error, not a panic.
MediumKEY-001commit d6e43113 files · +68 −30encryption at rest still open

The wallet seed lived in a database opened with crash-unsafe flags

What was wrong

Wallet::new opened LMDB with the node's "fast" flags: WRITE_MAP, MAP_ASYNC, NO_SYNC, NO_META_SYNC. The comment justified the lost durability by the state being reconstructible from the chain, which holds for the chain database and not for the 64-byte seed, the one thing in the data directory that cannot be rebuilt. LMDB documents that these flags can corrupt the database on system failure, and the app never forces a mnemonic backup.

What changed

  • The wallet environment uses LMDB's default fsync-on-commit durability; NO_READ_AHEAD and NO_TLS stay, since they do not affect durability.
  • The wallet directory is set to mode 0700 on Unix.
  • In-memory seed copies made during derivation and address recovery are wrapped in Zeroizing.
  • Test: set a seed, reopen the environment, read it back, check the directory mode.

Not done: encrypting the seed at rest with a user passphrase. It needs an unlock flow across the GUI, RPC and headless modes and is documented as open at the field.

MediumSIG-001commit 7a96a1d3 files · +174 −0

The mempool accepted transactions with fewer signatures than inputs

What was wrong

validate_transaction paired authorizations with spent outputs using zip, which stops at the shorter side, and verify_authorized_transaction batch-verified however many signatures were present. A two-input, one-signature transaction passed the address check for the signed input only and entered every mempool. Only block validation counted signatures, so the first miner to include it paid a BMM bribe for a block every node rejected, and the transaction stayed in the mempool to poison the next template.

What changed

  • verify_authorized_transaction returns NotEnoughAuthorizations or TooManyAuthorizations, like the body verifier.
  • validate_transaction checks the count explicitly before the per-input loop, with a new WrongAuthorizationCount error naming both numbers.
  • Tests model the exploit shape (attacker input plus victim input, one signature) and the over-signed mirror.
MediumDEP-001commit 4ba4c179 files · +384 −341

Swap monitoring was forced onto two hardcoded endpoints, one a public IP with credentials in source

What was wrong

An exact-match allowlist refused to start the app on any other URL, and the GUI showed the fields read-only. The BCH entry was a third-party public IP over plaintext HTTP with user/password embedded in the source. Whoever operated, compromised or sat on the path to that host could invent or hide fills for every default-config BCH user.

What changed

  • The allowlist, the exact-match check and the public endpoint are gone. Defaults are a local node on the chain's port with no credentials, offered as a starting point.
  • RpcConfig gains an optional cookie_file (Bitcoin Core style, read on every call, precedence over user and password); https:// works once the URL is editable.
  • RpcConfig::is_plaintext_remote drives a warning at startup, in the GUI and in the CLI when credentials and payment evidence would cross a network in the clear.
  • write_l1_config_file no longer discards entries that do not match a built-in and no longer overwrites existing ones. The GUI fields are editable, with a cookie-file field and a "use local default" button; two duplicate config parsers now use the library loader.
  • Files written by the previous version still load.
LowFND-006commit 3e8e6503 files · +238 −30rounding fixed by #123

Fill detection asked the node's wallet, which does not track the swap address

What was wrong

Detection called listunspent filtered by the swap's address. On a stock node that returns only outputs the wallet tracks, and an empty list rather than an error for anything else. Nothing in the flow imports the counterparty's address, so in the default configuration detection never fired: the swap expired, the creator reclaimed the escrow, and the filler's payment was gone. A fill spent before it was noticed disappeared from the list as well. The f64 truncation named by the same report had been fixed in #123.

What changed

  • Discovery runs scantxoutset with an addr(…) descriptor across the whole UTXO set, unioned with listunspent for nodes without it. The useless getreceivedbyaddress probe is dropped.
  • When only the wallet source is available and finds nothing, a warning names the address and the alternatives, so a blind node is visible rather than silent.
  • Once a swap's txid is known, query_and_update_swap fetches that transaction directly, so spending the fill no longer stalls confirmation tracking.
  • Tests use an in-process JSON-RPC server: payment seen by scantxoutset with an empty wallet; wallet fallback; no source at all is an error.
LowFND-007commit e78ff031 file · +135 −36consensus change

Deposits with unparseable addresses were credited to the all-zeros address

What was wrong

The conversion of an enforcer-reported deposit logged a warning and substituted Address::ALL_ZEROS when the bytes were not UTF-8 or did not parse. The comment said the deposit would be ignored; in fact it was credited to an address no key hashes to, burning the value and leaving an unspendable UTXO in the set for good.

What changed

  • Parsing fails with a dedicated InvalidDepositAddress error.
  • The BlockInfo conversion drops exactly that event with an error log, keeps every other event, and still fails on any other malformed field. Every node makes the same decision from the same bytes; the coins remain in the parent-chain escrow.
  • Tests: valid address credited; invalid UTF-8 and bad base58 are errors, never zeros; block info skips the bad deposit and keeps the good one.

Consensus change for any chain that has already seen such a deposit: old nodes hold a zero-address UTXO that new nodes do not.

LowKEY-002commit 91a288b8 files · +313 −32

The mnemonic was a command-line argument and reached trace logs on both sides

What was wrong

set-seed-from-mnemonic and recover-from-mnemonic took the phrase as a positional argument, so it landed in shell history and the process table. Both the server and the CLI client installed jsonrpsee's rpc_logger, which serialises whole requests at TRACE with a 1024-byte cap, well above a mnemonic's length; any trace-level run wrote seeds to stdout, the rolling log and the GUI console buffer.

What changed

  • The commands read the phrase from --mnemonic-file <path> (- for stdin) or a no-echo terminal prompt; --with-passphrase prompts, with confirmation, instead of taking a flag.
  • A RedactingRpcLoggerLayer in the shared rpc-api crate replaces the built-in logger on both sides: method name and id for every call, parameters and responses only for methods that carry no key material, batches by size. set_seed_from_mnemonic and generate_mnemonic are fully redacted.
LowKEY-003commit 399afd87 files · +133 −26

The GUI's passphrase field was ignored and the seed was shown in clear text

What was wrong

The seed pane rendered a masked passphrase field, but the set button passed only the phrase and the wallet hardcoded an empty passphrase. A user who typed one believed it protected the wallet and could not restore it elsewhere with the phrase and passphrase they had kept. The seed words were unmasked.

What changed

  • Wallet::set_seed_from_mnemonic takes the passphrase; a Wallet::seed_from_mnemonic helper is the single derivation path for the wallet and the RPC server.
  • The RPC method and CLI commands gain an optional passphrase; the GUI threads its field through, warns that the passphrase is part of the key, and masks the seed behind a reveal toggle.
  • Tests pin the BIP39 reference vector for the "TREZOR" passphrase and check that a wallet set with a passphrase refuses the same phrase with a different one.
