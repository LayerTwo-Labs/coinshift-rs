Coinshift Swap Mechanics

Every security property in the swap system follows from one question: is this fact in the blocks, or only on your node?

01 — The central idea

The boundary everything rests on

A Coinshift node knows two very different kinds of thing.

Block data is derived from the chain by replaying it. Every node that has the same blocks computes the same values, so block validation may rely on them: if a rule reads only from here, every node reaches the same verdict and the chain cannot split.

Local observation comes from somewhere else — a parent-chain RPC that this operator happens to run, an RPC call someone made against this node. It is real information, often the information that matters most, but it differs from node to node. A block validation rule that reads from here makes block validity depend on your configuration file.

The rule

Block validation reads only from the left. Anything on the right may inform the mempool, the wallet, or the UI — never whether a block is valid.

02 — Structure

Two validators, one payout rule

Because of that boundary, a SwapClaim is checked by two different functions depending on where it arrives.

The consensus half skips the first two deliberately. A node that has not yet seen the L1 fill — or that does not watch that chain at all — must still be able to accept a block containing the claim, or the chain splits along the lines of who configured what.

The two halves used to disagree about the last row, and that was the vulnerability. They no longer can: validate_swap_claim now performs its local checks and then calls the consensus function for everything about who gets paid. One rule, one implementation.

03 — Lifecycle

A swap with a fixed recipient

The simple case. Alice names Bob when she creates the swap, so the entitled address is block data from the very first transaction and nothing else is needed.

04 — Lifecycle

An open swap, reserved on-chain

An open swap has no recipient at creation — that is the point, since anyone should be able to fill it. So entitlement has to be established later, and it has to land in block data to be worth anything. That is what SwapAccept does.

The reservation is not permanent. It lapses at accepted_at_height + accept_expiration_blocks, after which the swap is open to anyone again. That window is what bounds griefing: someone can sit on a swap they never intend to fill, but each attempt costs an L2 fee and buys only one window.

The accept must also spend an input owned by the address it reserves for. Nothing exempts SwapAccept from the per-input authorization check, so that input carries a signature from the key — which is what stops anyone from parking every open swap for an address they do not control.

05 — The vulnerability

The attack, and why it now fails

Before this work, validate_swap_claim_consensus gated its payout check on the recipient existing:

if let Some(swap) = get_swap(..) && let Some(recipient) = swap.l2_recipient { … }

For an open swap, l2_recipient is None, so the whole check fell away. Block validation asked only that the claim spend the escrow — not where a single satoshi went. Combined with the authorization bypass for SwapPending inputs, that left open swaps with no payout protection at all on the block path.

Why the obvious patch was not enough

The first fix required an open claim to pay the l2_claimer_address the claim itself declares. That is a real invariant — the escrow can no longer be split, redirected, or burned — but on its own it stops nobody: an attacker declares her own address and pays herself in full. A payout rule is only as good as the source of the address it pays to.

06 — Design

Why reserving must come first

The intuitive design is to record the claimer at the moment you learn who paid — attach the L2 address to the L1 notification. It does not work, and the reason is worth seeing drawn.

The invariant

The reservation must be causally prior to the L1 payment. That ordering is the security property, not an implementation detail — it is the reason there is nothing to front-run.

07 — The remaining trust

What the parent chain still costs you

One fact never crosses into block data: whether the L1 payment actually happened. Consensus has no view of the parent chain, so "was Bob's BCH really sent?" is checked only by validate_swap_claim, only in the mempool, and only on nodes that run that chain's RPC. Three consequences follow, and they are worth separating.

Not a consensus problem

A node with no BCH RPC validates and connects a block containing a BCH swap claim exactly like everyone else, because the consensus half skips the L1 checks by design. Not running a parent chain never forks you.

It is a relay problem

The mempool half still requires swap.state == ReadyToClaim, which only advances if you poll that chain — query_and_update_swap skips the lookup entirely when no RPC is configured, and the swap stays Pending forever. So that node rejects an honest claim from a peer, and net_task.rs:1240 drops the peer on validation failure. Honest claims do not propagate through nodes that do not watch the chain, and relaying one costs you connections.

It is an unenforceable check

Worse than unwatched: the check is advisory even where somebody is watching. update_swap_l1_txid takes a txid and a confirmation count as arguments and never verifies them against the parent chain — the integration tests fill swaps with "11" repeated 32 times. That RPC is a defect in its own right and should verify or go away. But removing it would not close anything, because a miner never has to pass through it: block validation does not look at L1 at all, so any claim satisfying the consensus rules can simply be mined.

Honest nodes would never have relayed that claim. But relaying is not required to mine, and nothing about block validity depends on it. Follow that through and the shape of the residual risk is clear:

  • Open swaps. A miner reserves the swap — public, costs a fee, takes a block — then claims without ever paying on L1.
  • Pre-specified swaps. The named recipient is already the entitled claimer, so a miner who is that recipient claims without paying.

In both cases the maker loses the escrow. The reservation machinery does its job — it decides who may be paid, and that part is now enforced by every node — but nothing in block validation asks whether the other leg of the trade ever happened. The L1 leg is secured by whoever is watching and by the cost of misbehaving, not by consensus.

Closing it means proving the parent-chain payment to consensus: per-chain header sync, proof-of-work validation, and a merkle proof of the payment inside a parent-chain block, carried by the claim. That is a substantial project, and it is the honest price of the word "trustless" for the L1 leg.

08 — State

Two lifetimes, two owners

A swap carries two pieces of state that are easy to confuse and must never be merged. SwapState tracks what this node has observed about the L1 side; the reservation tracks what the chain says about entitlement.

The reservation has a much simpler life and a different owner. It is created by connect from a SwapAccept, cleared by disconnect, rebuilt by reconstruct_swaps, and expires by arithmetic rather than by a write — entitled_claimer_at compares the current height against accepted_at_height + accept_expiration_blocks each time it is asked. Nothing else may touch it; there is no RPC that writes a reservation.

Why it lives in its own table

Swap is persisted as bincode, a non-self-describing format, and State::get_swap reports a decode failure as Ok(None) — a silently missing swap. Adding a consensus-critical field to that record would make every swap written by an earlier build read as "no swap", and nodes would disagree about who may claim depending on when each upgraded: a consensus split introduced by a schema change. swap_reservations keeps the Swap record byte-identical, and a test destructures Swap without a .. pattern so that adding a field fails to compile.

Taker's checklist

  1. list-swaps — find an open swap and confirm it is unreserved.
  2. accept-swap --swap-id … — reserve it, and wait for the transaction to be mined.
  3. get-swap-status --swap-id … — confirm the reservation names your address. Do not skip this.
  4. Pay l1_amount on the parent chain, within the acceptance window.
  5. claim-swap --swap-id … once confirmations are reached.
