The shape of it

One new output variant, two spend rules, a BTC HTLC built entirely in the wallet, and the deletion of the parent-chain observer from anything that decides who gets paid.

Consensus never learns what BTC is. The information travels through a revealed preimage instead of an observation, which is why this is the smallest of the four options rather than the largest. Straight to the phases →

01 — The protocol

What we are building

A hash-timelocked exchange. Both legs lock to the same secret; revealing it on one chain to take payment publishes it on that chain, which lets the counterparty take the other leg.

The maker holds Coinshift coins and wants BTC. They pick a secret s, publish H = sha256(s), and lock their coins so that either the taker can spend them by revealing a preimage of H, or the maker can reclaim them after a deadline. The taker mirrors that on BTC with a standard P2WSH HTLC on the same H and a shorter deadline. The maker takes the BTC — which necessarily publishes s — and the taker reads s off the BTC chain and takes the Coinshift coins.

Neither chain ever observes the other. Coinshift consensus checks one thing about the swap's completion: that a supplied preimage hashes to the committed value.

02 — Before starting

Prerequisites that block the start

Two of these are open pull requests and one is an open issue. None is optional, and the middle one is a genuine dependency rather than tidiness.

  1. PR #137 — the build fixes. main does not compile: the rcgen 0.13 → 0.14 bump renamed CertifiedKey::key_pair. Nothing can be built or tested until this lands.
  2. PR #138 — expiry decided from block data. A real dependency. HashLocked refunds are the same class of height-based release that expiry currently gets wrong, gating a consensus decision on node-local state. Land the fix and its regression test first, so the correct pattern is in the tree before a second user of it arrives.
  3. Issue #141 — swap_creation_open_fill. The swap integration test is red. It is also the file the new end-to-end test will be built beside, so it needs to be green to be a baseline.
Worth noticing

#141 fails because the test reserves a swap for a freshly generated, unfunded address, and validate_swap_accept requires the reserver to spend an input they own. That failing test is the same fact this whole plan rests on: a taker must already hold Coinshift coins.

Phase 3 is where the thought goes, because it is the phase that decides who gets paid.

04 — Care required

Three ways to get this wrong

Use SHA-256, not blake3

The preimage has to satisfy Bitcoin's OP_SHA256. This codebase reaches for blake3 elsewhere — SwapId is a blake3 digest — and copying that habit here produces two locks that cannot be opened by the same secret. The swap then silently stops being atomic: each side is refundable, neither is claimable. Pin it with a test that constructs a real BTC HTLC script and checks the hash matches the L2 output's.

The initiator gets the longer timeout

The maker knows s, so the maker's own lock must expire last: T_short on BTC, T_long on Coinshift, with enough margin between them for the taker to see the reveal and act. Invert it and the maker can take the BTC and then reclaim their escrow once the taker's window has closed — a complete theft, from a two-character mistake in a constant.

Make the margin explicit

The gap must cover BTC confirmation latency plus L2 block time plus a safety factor, and it belongs in a named constant with the reasoning in its doc comment — not as two numbers that happen to differ.

Append-only — habit now, requirement later

Both Content and TxData are Borsh-encoded by variant index into the block body, and therefore into the merkle root. With no production chain, inserting a variant mid-enum would cost nothing today: there are no records written under the old numbering to misread.

Append anyway. It is free, and the first time it actually matters will be the first time someone forgets it. The rule is worth having as muscle memory before it is worth having as a constraint.

Correction

An earlier draft said ParentChainType already has a borsh_discriminants_are_stable test to copy. It does not — that test lives only on feat/parent-chain-phase-9-docs and has never been on main. Phase 1 therefore writes the guard rather than copying one: output_content_borsh_discriminants_are_stable in lib/types/transaction.rs, which pins each variant's index and names the consequence in its assertion message.

05 — Proof

How each phase is proved

The current swap tests cannot distinguish a working swap from one that merely believes it worked, because the L1 side is fabricated — the integration tests fill swaps with a made-up txid. Under this design that stops being possible, and the tests get correspondingly better.

  • Phase 1–2. Borsh round-trip and discriminant stability for both enums.
  • Phase 3. Claim with a correct preimage succeeds; with a wrong one fails; refund before timeout_height fails; at exactly timeout_height succeeds. The boundary is where this kind of rule usually breaks — reservation_expiry_boundary() at lib/types/swap.rs:L527 is the pattern to copy.
  • Phase 3, consensus parity. Two states that disagree about everything node-local must reach the same verdict on the same claim — the shape of the regression test in PR #138.
  • Phase 5. A real regtest BTC HTLC: fund it, claim it with the preimage, and assert the secret is recoverable from the spending transaction. This is the test that proves the two legs share a hash function.
  • End to end. Both legs on regtest, plus the two unhappy paths — the taker never pays (maker refunds), and the maker never reveals (taker refunds). Neither may lose money.

06 — Try it

Running it yourself

Two ways in: the automated end-to-end test, or the CLI by hand. The test is the faster answer to "does this work"; the CLI is how you get a feel for the shape of a swap.

The end-to-end test

One command, about forty seconds once the dependencies are built. It stands up a real regtest stack — bitcoind, the BIP300 enforcer, electrs, a Coinshift node — locks an escrow, claims it with the secret, then locks a second one and refunds it past its deadline.

scripts/run_integration_tests.sh --tests hash_lock_lifecycle

Expect test hash_lock_lifecycle ... ok. The first run compiles the enforcer and electrs from source and takes several minutes; after that they are cached and it is quick.

If it dies with "unexpected argument"

error: unexpected argument '--serve-json-rpc-addr' found means you are on a branch without the runner fix. The suite downloads the published latest enforcer while the test harness is pinned to a9ca43d, the two disagree on the CLI, and nothing runs at all. Fixed on this branch and in isolation as a one-file change against main.

By hand, with the CLI

The node needs the enforcer running, so bring up the regtest stack first (docs/SETUP_ORDER.md). Then, with C="coinshift_app_cli --rpc-url http://127.0.0.1:6255":

1. Generate the secret and the Bitcoin contract it commits to. Keep the secret; publish nothing but the commitment until you are ready to claim.

$C new-swap-secret \
    --claim-pubkey <taker btc pubkey> \
    --refund-pubkey <taker btc pubkey for refund> \
    --bitcoin-timeout-height <btc height> --network regtest

You get back secret_hex, commitment_hex, the P2WSH bitcoin_address the taker funds, and witness_script_hex. Check that script independently — nothing here asks you to take our word for it:

bitcoin-cli decodescript <witness_script_hex>

2. Get a safe deadline pair. This derives the Coinshift deadline rather than letting you pick both, because the party holding the secret has to expire last and an argument list is an easy place to swap two numbers.

$C suggest-swap-deadlines \
    --bitcoin-height <btc tip> --bitcoin-blocks 100

3. Lock the Coinshift leg, then mine a block.

$C create-hash-lock \
    --value-sats 5000000 \
    --commitment-hex <commitment> \
    --claimant <taker L2 address> \
    --timeout-height <coinshift_timeout> \
    --fee-sats 1000

4. See it, including whether its deadline has passed:

$C list-hash-locks

5a. Claim — the taker, holding the secret:

$C claim-hash-lock <txid> <vout> \
    --secret-hex <secret> --fee-sats 1000

5b. Or refund — the maker, once refundable_now is true:

$C refund-hash-lock <txid> <vout> --fee-sats 1000
Worth trying the failures too

Claim with the wrong secret, or refund before the deadline. Both are refused, and those refusals are the actual product — a system that pays out correctly but also pays out incorrectly is not a swap system. The test asserts both.

What you cannot do yet

Run a real cross-chain swap. The Bitcoin script and address are built and checkable, but nothing funds or spends the Bitcoin leg — that needs key management and an RPC backend. So today you can exercise the Coinshift half completely and inspect the Bitcoin half, which is enough to see the mechanism but not to move BTC.

07 — What it caught

What the test found

It failed on its first real run, twice, and both were genuine bugs rather than test problems. Recorded because the shape of them is instructive.

A claim could not pay a fee

The rule requires the claimant to be paid the lock's value in full; the wallet took the fee out of that payout. Every claim with a non-zero fee was rejected.

The rule was right and the wallet was wrong. The claim path is exempt from the address check, so paying the claimant in full is the only thing standing between the secret and the money — it cannot be relaxed to make room for a fee. The claimer now brings an ordinary coin of their own, which is how claiming a Bitcoin HTLC works too.

The refund rule was redundant, and the redundancy cost money

Refunds were required to pay the output's own address. But the refund path takes no authorization exemption — Output::address signs for it like any ordinary coin — so only the owner could ever spend it, and where they then send their own money is not consensus's business.

The rule added nothing, and by demanding payment in full it left no room for a fee either, so every refund the wallet built was rejected as well. The only rule now is the deadline.

The test that replaced it

Deleting a rule needs the property that made it safe pinned in its place. the_refund_path_is_not_exempt_from_the_address_check asserts that refunds are not exempt and claims are. If that exemption ever grows to cover refunds, the payout rule has to come back — and this is what fails first.

The lesson worth keeping

Both bugs had reasoning written next to them explaining why they were correct. One commit message argued at length that taking the fee from the payout was safe "so no payee is silently underpaid". It was simply wrong, and no amount of re-reading would have found it. A regtest run found both in forty seconds.

Which is also the argument for the runner fix: while the suite could not start, none of this was findable. Two real bugs sat behind a harness that died before running anything.

08 — Honest limits

What is still not trustless

An atomic swap removes the trusted party. It does not remove counterparty risk, and saying "this makes it trustless" without the rest would be the same overclaim the README spent a year making.

What genuinely goes away

  • A miner claiming an escrow without paying. There is no longer any such thing as a claim based on an alleged payment, so there is nothing to fabricate.
  • A lying RPC deciding who gets paid. Consensus checks a hash preimage and nothing else. An endpoint that lies to you can only cause you to miss a deadline.
  • Node-local state gating consensus. Every input to a spend decision is derivable from blocks.
What remainsWhy it cannot be designed awayWhat reduces it
You have to watch Once the maker reveals the secret to take the Bitcoin, the taker must claim before the Coinshift escrow expires. Miss the window and the maker refunds it and keeps the Bitcoin. Nobody broke a rule — the taker looked away. REVEAL_SAFETY_BLOCKS, and an automated watcher rather than a person.
The maker holds a free option They choose whether to reveal at all. If the price moves against them they walk; the taker refunds, whole but out fees and a round trip. Inherent to who generates the secret. Short windows, a forfeitable maker bond, reputation.
Deadline ordering is ours to get right Consensus on either chain sees one leg and cannot check the relationship between two. Nothing on-chain can catch an inverted pair. SwapDeadlines refuses to construct one — but it is our code, not a rule.
Deep reorgs A reorg past the confirmation depth on either chain, after one leg has settled, leaves the two legs disagreeing. Depth is the only mitigation anyone has. Confirmation depth, chosen against reorg cost.
The parameter this turns on

REVEAL_SAFETY_BLOCKS is how long a taker may look away, and it was 12 blocks — two hours, which is comfortable for a daemon and far too short for a person. It is now 144, roughly a day.

The cost is locked capital on both sides when a swap is abandoned. That is a product decision rather than an engineering one, and it belongs with whoever knows how this will actually be used — the same bucket as the maker bond.

The claim we can actually make

Trustless, not risk-free, and it requires participation. There is no third party to trust and no endpoint whose honesty matters to anyone but its own operator. There is still a counterparty who can waste your time, and a window you have to stay awake for.

That is a straightforwardly better trade than trusting an RPC. It is not the same as safe to start and forget, and the README now says so in those words.

09 — Corrections

Where the documentation lied

Three places where a document asserted something that was not true, found while doing this work. Recorded rather than quietly corrected, because a contradiction that is silently patched teaches nobody anything, and the same one grows back.

The README said the swap system was trustless

First sentence, first line: "a BIP300-style sidechain node with a trustless L2 <-> L1 swap system". It was not trustless. validate_swap_claim_consensus never inspected a parent-chain fact, so a miner could claim an escrow for a payment that never happened — the vulnerability this entire branch exists to close.

Every document in docs/specs/ had been saying so for some time. The README, which is what anyone reads first, said the opposite. The claim is now replaced by a note that states what is actually true and says the README used to say otherwise.

COINSHIFT_HOW_IT_WORKS contradicted itself, 130 lines apart

"Not implemented (doc vs code)""Current Limitations"
L1 transaction uniqueness — not implementedUniqueness — enforced
Reject confirmations == 0 — not implementedConfirmations — enforced and tested
Block inclusion — not implementedBlock inclusion — enforced and tested

The second column was right. The code does all three and there are integration tests named after them. The first table had gone stale and nobody noticed, because nothing reads a document end to end looking for two halves that disagree.

The stale table is gone, replaced by the more useful fact: each of those checks runs against a node-local RPC answer, so none of them makes the parent-chain leg trustworthy, and consensus asks none of them.

And two in this document's own commits

A commit message argued at length that taking the fee out of a claim's payout was safe, "so no payee is silently underpaid below what the spend rules require". The spend rules require payment in full; the reasoning was simply inverted, and every claim with a fee was rejected. A second commit reasoned that refunds must pay the output's own address, which was redundant with the signature that authorises them and blocked fees the same way.

An earlier draft of this plan also stated that ParentChainType already had a borsh_discriminants_are_stable test to copy. It does not — that test exists only on feat/parent-chain-phase-9-docs, and phase 1 had to write one.

The pattern

Every one of these was reasoning written next to the thing it was wrong about. Confident, specific, and load-bearing. None of them survived contact with a regtest run, and the two spend bugs were found in forty seconds by a test that had been unable to start for months.

The practical lesson is not "write better comments". It is that a claim about behaviour belongs in a test, where being wrong is loud, rather than in prose, where being wrong is invisible and gets quoted back as evidence.

10 — Rollout

Getting it into the world

Nothing is in production, so this ships as an ordinary change rather than a fork. That is the single biggest thing working in this plan's favour, and it has a shelf life.

The three consensus changes queued up — the expiry fix in #138, the SwapAccept binding already merged in #135, and this one — would each need a coordinated deployment against a live chain. Against no chain they need a merge and a rebuilt regtest. Landing them now costs a fraction of what landing them later will.

There is a caveat worth knowing rather than worrying about: the README advertises a node at coinshift.bip300.xyz, and lib/net/mod.rs compiles in signet seed nodes. Any chain those hold will not survive these changes. If that data is disposable, this is free; if it is not, it is the one thing to check before merging.

What this buys the plan

No migration path for existing swaps. No activation height. No version negotiation between old and new nodes. No window during which both rule sets must be tolerated. Every one of those is a place bugs live, and none of them has to be built.

One documentation change ships with it

The README calls the swap system trustless. With this merged that becomes true, and the sentence can stay. Until then it should say what is actually the case, which is the one part of this plan that costs nothing and can be done today.
