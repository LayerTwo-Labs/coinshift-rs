The shape of it

One new output variant, two spend rules, a BTC HTLC built entirely in the wallet, and the deletion of the parent-chain observer from anything that decides who gets paid.

Consensus never learns what BTC is. The information travels through a revealed preimage instead of an observation, which is why this is the smallest of the four options rather than the largest. Straight to the phases →

01 — The protocol

What we are building

A hash-timelocked exchange. Both legs lock to the same secret; revealing it on one chain to take payment publishes it on that chain, which lets the counterparty take the other leg.

The maker holds Coinshift coins and wants BTC. They pick a secret s, publish H = sha256(s), and lock their coins so that either the taker can spend them by revealing a preimage of H, or the maker can reclaim them after a deadline. The taker mirrors that on BTC with a standard P2WSH HTLC on the same H and a shorter deadline. The maker takes the BTC — which necessarily publishes s — and the taker reads s off the BTC chain and takes the Coinshift coins.

Neither chain ever observes the other. Coinshift consensus checks one thing about the swap's completion: that a supplied preimage hashes to the committed value.

02 — Before starting

Prerequisites that block the start

Two of these are open pull requests and one is an open issue. None is optional, and the middle one is a genuine dependency rather than tidiness.

  1. PR #137 — the build fixes. main does not compile: the rcgen 0.13 → 0.14 bump renamed CertifiedKey::key_pair. Nothing can be built or tested until this lands.
  2. PR #138 — expiry decided from block data. A real dependency. HashLocked refunds are the same class of height-based release that expiry currently gets wrong, gating a consensus decision on node-local state. Land the fix and its regression test first, so the correct pattern is in the tree before a second user of it arrives.
  3. Issue #141 — swap_creation_open_fill. The swap integration test is red. It is also the file the new end-to-end test will be built beside, so it needs to be green to be a baseline.
Worth noticing

#141 fails because the test reserves a swap for a freshly generated, unfunded address, and validate_swap_accept requires the reserver to spend an input they own. That failing test is the same fact this whole plan rests on: a taker must already hold Coinshift coins.

Why phase 1 is small and phase 3 is not

Content has 25 edges and every one of them is inside lib/types/transaction.rs. Adding a variant is exhaustive-match work the compiler drives: DefaultRepr L292, HumanReadableRepr L308, both From impls L390 and L410, GetValue L378, schema_ref L373, Borsh at L470/L481, ToSchema at L491/L497.

Phase 3 is where the thought goes, because it is the phase that decides who gets paid.

04 — Care required

Three ways to get this wrong

Use SHA-256, not blake3

The preimage has to satisfy Bitcoin's OP_SHA256. This codebase reaches for blake3 elsewhere — SwapId is a blake3 digest — and copying that habit here produces two locks that cannot be opened by the same secret. The swap then silently stops being atomic: each side is refundable, neither is claimable. Pin it with a test that constructs a real BTC HTLC script and checks the hash matches the L2 output's.

The initiator gets the longer timeout

The maker knows s, so the maker's own lock must expire last: T_short on BTC, T_long on Coinshift, with enough margin between them for the taker to see the reveal and act. Invert it and the maker can take the BTC and then reclaim their escrow once the taker's window has closed — a complete theft, from a two-character mistake in a constant.

Make the margin explicit

The gap must cover BTC confirmation latency plus L2 block time plus a safety factor, and it belongs in a named constant with the reasoning in its doc comment — not as two numbers that happen to differ.

Append-only — habit now, requirement later

Both Content and TxData are Borsh-encoded by variant index into the block body, and therefore into the merkle root. With no production chain, inserting a variant mid-enum would cost nothing today: there are no records written under the old numbering to misread.

Append anyway. It is free, it keeps borsh_discriminants_are_stable meaningful rather than something to be edited whenever it complains, and the first time it actually matters will be the first time anyone forgets it. The rule is worth having as muscle memory before it is worth having as a constraint.

05 — Proof

How each phase is proved

The current swap tests cannot distinguish a working swap from one that merely believes it worked, because the L1 side is fabricated — the integration tests fill swaps with a made-up txid. Under this design that stops being possible, and the tests get correspondingly better.

  • Phase 1–2. Borsh round-trip and discriminant stability for both enums.
  • Phase 3. Claim with a correct preimage succeeds; with a wrong one fails; refund before timeout_height fails; at exactly timeout_height succeeds. The boundary is where this kind of rule usually breaks — reservation_expiry_boundary() at lib/types/swap.rs:L527 is the pattern to copy.
  • Phase 3, consensus parity. Two states that disagree about everything node-local must reach the same verdict on the same claim — the shape of the regression test in PR #138.
  • Phase 5. A real regtest BTC HTLC: fund it, claim it with the preimage, and assert the secret is recoverable from the spending transaction. This is the test that proves the two legs share a hash function.
  • End to end. Both legs on regtest, plus the two unhappy paths — the taker never pays (maker refunds), and the maker never reveals (taker refunds). Neither may lose money.

06 — Rollout

Getting it into the world

Nothing is in production, so this ships as an ordinary change rather than a fork. That is the single biggest thing working in this plan's favour, and it has a shelf life.

The three consensus changes queued up — the expiry fix in #138, the SwapAccept binding already merged in #135, and this one — would each need a coordinated deployment against a live chain. Against no chain they need a merge and a rebuilt regtest. Landing them now costs a fraction of what landing them later will.

There is a caveat worth knowing rather than worrying about: the README advertises a node at coinshift.bip300.xyz, and lib/net/mod.rs compiles in signet seed nodes. Any chain those hold will not survive these changes. If that data is disposable, this is free; if it is not, it is the one thing to check before merging.

What this buys the plan

No migration path for existing swaps. No activation height. No version negotiation between old and new nodes. No window during which both rule sets must be tolerated. Every one of those is a place bugs live, and none of them has to be built.

One documentation change ships with it

The README calls the swap system trustless. With this merged that becomes true, and the sentence can stay. Until then it should say what is actually the case, which is the one part of this plan that costs nothing and can be done today.
