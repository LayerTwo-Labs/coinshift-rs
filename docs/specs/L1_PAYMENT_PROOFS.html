L1 Payment Proofs

Making the parent-chain half of a swap something every node checks, instead of something each node takes on faith.

01 — Problem

What is unverified today

A swap has two legs. The L2 leg is enforced by consensus: the escrow is locked when SwapCreate connects, and since SwapAccept landed, only the address named by a live reservation can be paid. Every node checks both from block data.

The L1 leg is not checked by anything that binds. validate_swap_claim_consensus never asks whether the parent-chain payment happened, because it has no way to find out. The only thing that looks is validate_swap_claim, in the mempool, on nodes that happen to run that chain's RPC — and a miner is under no obligation to be one of them.

Consequence

A miner can take any swap's escrow without paying on L1. For an open swap: reserve it, then claim. For a pre-specified swap: be the named recipient, then claim. Honest nodes would refuse to relay either claim, but relaying is not required to mine, and the resulting block is valid everywhere.

Two smaller defects sit on top of this. update_swap_l1_txid accepts a txid and a confirmation count as arguments and never checks them against the parent chain — the integration tests fill swaps with "11" repeated 32 times. And swaps_by_l1_txid, which stops one L1 payment being reused across swaps, is node-local, so it constrains only the node that holds it.

02 — The constraint

Where the check has to run

It is tempting to fix this by making update_swap_l1_txid verify against the configured RPC before it writes. That is worth doing on its own merits, and it is in the cheapest option below — but it does not change the trust model at all. The result is still a local observation: absent on nodes that do not run the chain, different between nodes that do, and trivially skipped by anyone building a block.

For the L1 leg to be trustless, the check must be reproducible by every node from the block itself. That means three things, and this spec is really just those three:

  1. the claim carries a proof rather than an assertion;
  2. nodes hold a proof-of-work-validated header chain for the parent chain, as consensus state;
  3. the confirmation depth is measured against a deterministic anchor, not against wall-clock chain tips.

Point 2 is the one that decides scope, because the node already satisfies it for exactly one chain: the mainchain it is merge-mined against. It satisfies it for no other.

03 — Mechanism

The proof, and what carries it

TxData::SwapClaim already has the field. proof_data: Option<Vec<u8>> exists, is threaded through the wallet and the validators, and is set to None at every single call site. This is what it was reserved for.

What the archive already holds

main_header_infos gives, for every mainchain block the node knows: block_hash, prev_block_hash, height, work. Ancestry is enforced on insert and BMM commitments are verified. It is a real, proof-of-work-validated header chain.

What it does not hold is merkle roots. BlockHeaderInfo has no such field and BlockInfo carries only the BMM commitment and the peg events. So inclusion proofs cannot be checked against it directly.

That gap closes without touching the enforcer. Have the claim supply the raw 80-byte header. Consensus hashes it, requires the result to be a block hash the archive already knows on the main ancestry — and then reads the merkle root out of the header it has just authenticated. The proof carries its own trusted root.

Proof encoding

Borsh, in proof_data, versioned so the format can move without a second consensus change:

struct L1PaymentProof {
    version: u8,           // 0
    header: [u8; 80],      // raw parent-chain block header
    tx_index: u32,         // position of the tx in the block
    branch: Vec<[u8; 32]>, // merkle path, leaf to root
    rawtx: Vec<u8>,        // the L1 transaction
}

Bitcoin Core produces the middle two directly: gettxoutproof returns a serialized merkle block containing the header and the branch, and getrawtransaction the last. The wallet assembles the proof at claim time from whatever RPC the claimer runs; it never needs to be trusted, because consensus re-derives everything from it.

Verification, in order

  1. sha256d(header) is a block hash present in main_header_infos and on the main ancestry of the L2 block being validated. Yields a trusted height and a trusted merkle_root.
  2. sha256d(rawtx) gives txid; folding it up branch according to tx_index reproduces merkle_root. The branch length must equal ceil(log2(tx_count)) for the block, and any step whose two hashes are equal is rejected — otherwise the CVE-2012-2459 duplicate-hash trick forges inclusion.
  3. The outputs of rawtx pay at least l1_amount to the script for l1_recipient_address, parsed for the swap's parent_chain network.
  4. An OP_RETURN output commits to this swap and claimer — see §5.
  5. watermark_height − height ≥ required_confirmations — see §4.
  6. This txid has not been used by another swap, checked against consensus state rather than the node-local index.

All six are pure functions of block data plus state derived from block data. Two nodes with the same chain always agree.

04 — Mechanism

Anchoring the confirmation count

"Six confirmations" has no fixed meaning at validation time. Two nodes at different mainchain sync heights compute different depths for the same proof, and a rule that depends on when you ask is exactly the class of bug this whole branch has been about.

The fix is to measure depth against a mainchain height that is itself consensus state. Two-way peg data is already applied deterministically as each L2 block connects — that is what makes deposits and withdrawal bundles work — so State can carry a mainchain height watermark advanced by the same path. Depth is then watermark − proof.height, evaluated at the L2 block being validated, and it is identical on every node forever.

Alternative, and an open question

The other candidate anchor is the mainchain block that BMM-committed the L2 block being validated. It is appealing because BMM already ties the two chains together — but a sidechain block can be committed by more than one mainchain block, so "the" BMM block is not unique, and picking one is a rule that has to be specified and defended. The watermark avoids that. Flagged in §9 rather than settled here.

05 — Mechanism

Binding the payment to the swap

Proving that a payment happened is not the same as proving it was for this swap. Matching on recipient address and amount is circumstantial: two swaps to the same address for the same amount are indistinguishable, which is precisely why an L1-txid uniqueness check had to be bolted on.

Require the L1 transaction to carry an OP_RETURN output committing to both the swap and the claimer:

OP_RETURN  PUSH(56)
    "CSFT"                    4 bytes   magic
    swap_id                  32 bytes
    l2_claimer_address       20 bytes

56 bytes sits inside the standard 80-byte relay limit with room spare. Consensus reads the claimer out of the commitment and pays that address — so entitlement is established by the act of paying, which is the only thing that should ever have established it.

This demotes SwapAccept

Front-running becomes impossible at the source: nobody can produce a proof of a payment committing to their address without making that payment. The reservation exists only because consensus is blind to L1; once it can see, the reservation is no longer a security mechanism.

It keeps one honest use — stopping two takers from both paying L1 for the same swap, where one of them eats the loss. That is coordination, and it is worth keeping for it. But the acceptance window, the lapse rule and the griefing analysis all stop being load-bearing, and could be relaxed or dropped.

07 — The decision

Scope: three options

The mechanism above works for one chain: the one the sidechain is merge-mined against, because that is the only chain whose headers the node has. Everything else is a question of how far to go.

Option A

Harden what exists

Make update_swap_l1_txid verify against the configured RPC, or remove it. Narrow ParentChainType to the chains you actually watch. No proofs, no consensus change.

The recommendation is B. It is the option where the word "trustless" in the README becomes true rather than aspirational, and it needs no new data source, no relay, and no incentive design — the header chain is already there and already validated, because the sidechain cannot function without it.

C is a different project wearing the same name. Each chain needs its own difficulty-adjustment implementation — BCH's ASERT, Litecoin's scrypt and retarget schedule — validated in consensus, plus someone paying to relay headers forever, plus the assumption that a low-hashrate chain cannot be outrun cheaply enough to forge a proof. It is defensible for a chain with a real reason to be supported. It is not defensible as a side effect of an enum having five variants.

Which makes the parent-chain question easy

Under B, chains you cannot prove anything about should leave ParentChainType. Keeping BCH and LTC as selectable options while only the mainchain is verifiable ships two tiers of security under one name — and LTC currently resolves to Network::Bitcoin as an acknowledged placeholder, so its addresses are wrong regardless.

09 — Unresolved

Open questions

  • Watermark or BMM anchor. The watermark is simpler and sidesteps multiple BMM commitments to one L2 block. A BMM anchor is tighter to the actual chain relationship. Needs a decision before the state work starts.
  • Confirmation depth. Six is the current default for BTC. Under a proof regime the depth is the entire security parameter for the L1 leg, so it should be chosen against reorg cost rather than inherited from convention.
  • Parent-chain reorgs after payout. A reorg deeper than the required depth, after the claim has connected, leaves L2 having paid for a payment that no longer exists. Depth is the only mitigation; worth stating the accepted risk explicitly.
  • Keep or drop SwapAccept. It stops two takers racing and losing money, which is real. It also adds a transaction, a fee and a wait to every open-swap fill. A judgement call once it is no longer carrying security.
  • Proof size. Header 80 B, branch about 320 B, transaction a few hundred — call it 1 KB per claim against the body size limit. Not a problem, worth noting.
  • Migration. None needed; nothing is deployed. If that changes before this lands, it is a consensus change and wants the same treatment as the current branch.
