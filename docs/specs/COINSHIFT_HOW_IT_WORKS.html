How Coinshift Works

A BIP300 sidechain with two quite different mechanisms bolted together — a two-way peg that consensus verifies, and a swap system that until recently it did not.

The one distinction to hold on to

Coinshift talks to two different chains, and almost every confusion in this system comes from conflating them.

The mainchain is what it is merge-mined against and pegged to — deposits, withdrawals, BMM. The parent chain is what a swap pays out on. They can be, and here are, different chains. The node holds a verified header chain for the first and nothing at all for the second. Why that matters →

01 — The distinction

Two chains, not one

A sidechain has a mainchain. A swap has a parent chain. Coinshift has both, they are not the same thing, and the difference decides what can be verified.

The mainchain is the chain Coinshift is merge-mined against. The BIP300 enforcer feeds the node its headers, which land in the archive with ancestry enforced on insert, so the node holds a real proof-of-work-validated header chain for it. Deposits, withdrawals and block validity all rest on that.

The parent chain is whichever chain a swap's L1 leg is paid on. The node has no header chain for it, no proof of work, and no way to check anything it is told about it. It asks a configured RPC endpoint and believes the answer.

The sidechain can be merge-mined against one chain while swapping against another — and in this deployment it is. That is not a quirk; it is the fact that makes the swap leg hard to secure, and it is spelled out at length in Proving the Parent Chain.

03 — The peg

The two-way peg

Moving value between the mainchain and Coinshift. This half is verified end to end, and is the model for what the swap leg should look like.

A deposit is a mainchain transaction paying a specially formatted address. The enforcer reports it; the node applies it only from a mainchain block already in its archive, so a deposit cannot be invented by a peer. A withdrawal is the reverse and slower: outputs are bundled, the bundle is submitted to the mainchain, and its fate — confirmed or failed — comes back as two-way peg data matched by M6id.

04 — The swap

The swap lifecycle

Four steps, three of them consensus and one of them not — and the one that is not is where every problem lives.

Alice locks L2 coins in escrow with SwapCreate. Bob reserves the swap with SwapAccept, which requires him to spend an input he owns, proving control of the address he is reserving for. He then pays on the parent chain. Finally he claims the escrow with SwapClaim.

The reservation must come before the payment, and that ordering is the security property rather than a convenience. Recording who is entitled after the payment would be front-runnable: anyone watching could name their own address first and take an escrow someone else had already paid for. Reserving first leaves nothing to front-run — a reserver who has only reserved has only reserved.

block data — every node agrees node-local observation — nodes differ unverified by anything

05 — The idea

Block data versus local observation

If you take one thing from this document, take this. Every security property in the system follows from which side of this line a fact sits on.

Block data is anything derivable from the chain: which outputs are locked, who holds a reservation, what height it is. Two nodes with the same blocks compute the same answer, always. Consensus can safely depend on it.

Local observation is anything a node learned by asking something outside the chain — overwhelmingly, a parent-chain RPC. It differs between nodes by endpoint, by timing, and by whether anyone is lying. Consensus cannot depend on it, and where it accidentally does, the result is not a delay or a disagreement but a chain split.

That is not hypothetical. Swap expiry used to skip swaps a node had locally advanced to ReadyToClaim, so two honest nodes that disagreed about an L1 payment released different escrow locks — and then accepted and rejected each other's blocks in both directions. The fix was to decide expiry from block data alone.

The rule that falls out of it

A value may gate a consensus decision only if every node derives it from blocks. Everything else is advisory: fine for a wallet to act on, fine to show in a UI, never allowed to decide who gets paid.

06 — Verification

What actually confirms a payment

The two-way peg and the swap leg both talk about "confirming a payment on another chain". They mean completely different things by it.

For deposits and withdrawals

  1. A header chain. Mainchain blocks are stored only if their parent is already present, so the archive holds one connected, validated chain.
  2. Proof of work. Each header carries its work; total work accumulates along the chain, and tip selection uses it. A peer's claimed total work is checked against the archive's own computation.
  3. BMM. A sidechain block counts as verified when a mainchain block commits to its hash, with prev_main_hash consistency and a valid commitment to the parent in the main ancestry.
  4. Provenance. Peg events are applied only from mainchain blocks already in the archive — never from a block a peer asserts.
  5. Identity. Withdrawal bundle events are matched by M6id, so a verdict lands on the bundle it belongs to.

For swaps

One thing: an RPC call to the configured endpoint for that parent chain, matching by address and amount, and taking the confirmation count from the answer.

There is no header chain for the swap parent chain, no proof of work, no merkle proof of the transaction in a block, and no second opinion. There is also no BMM report mechanism — despite what older documentation claimed, BMM here is merge-mining and nothing else.

What the checks are worth

L1 txid uniqueness, rejecting zero confirmations, and requiring block inclusion are implemented and tested. But each runs against a node-local RPC answer, so they are exactly as honest as the endpoint you configured, they differ between nodes, and consensus consults none of them. They reduce accidents. They do not stop an attacker.

An earlier version of this document listed those three as unimplemented in one section and enforced in another, 130 lines apart. The second was right; the contradiction is recorded in the plan's §08 rather than quietly patched.

Why reservations are their own table

Swap is stored as bincode, and State::get_swap reports a decode failure as Ok(None). Adding a consensus-critical field to that struct would make records written by an earlier version read as "no swap" — and nodes would then disagree about who may claim, depending on when each upgraded. A separate database keeps the record format frozen, and keeps consensus state physically apart from the node-local fields on Swap, which is the distinction that got blurred in the first place.

08 — Trust

The trust model

Stated plainly, because the README managed to state it wrongly for a long time.

What is trustless. The two-way peg, block validity, and the L2 half of a swap. Escrow locks when SwapCreate connects; only the address named by a live reservation can be paid; expiry is decided from block data. Every node checks all of it.

What is not. The parent-chain leg. Consensus never inspects an L1 fact, so a miner can claim a swap escrow for a payment that never happened and every node will accept the block. Point a chain only at an endpoint you run — but understand that this protects you from a lying endpoint, not from a miner, because the miner does not need to lie to anyone.

Where this is going

Proving the Parent Chain works through the four ways to close that gap and why only one survives contact with our chain layout. Building the Atomic Swap is the plan, the runbook, and the current state — the Coinshift leg and a real Bitcoin HTLC both pass on regtest today.

The shape of the fix is worth stating here because it explains the whole document: an atomic swap replaces the question consensus cannot answer — did a payment happen on another chain? — with one it can, which is does this preimage hash to the committed value? The amber column in Figure 1 stops being something to secure and becomes something to delete.
